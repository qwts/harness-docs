# Junie corrections log

**Verified:** 2026-11-15

| Claim | Verdict | Correction |
|---|---|---|
| Junie stacks `.junie/AGENTS.md`, root `AGENTS.md`, `.junie/playbook.md`, and `.junie/rules/*.md` together. | ❌ FALSE | `.junie/AGENTS.md`, when it exists, “is used exclusively; no other guidelines files are combined with it.” The `AGENTS.md` + playbook + rules concatenation is the fallback path, with legacy `.junie/guidelines.md` last. |
| Project-level guidelines always win over global ones, and conflicting content is merged. | ❌ FALSE | Both are included and marked, and project wins on conflict — but identical content is not duplicated: “Junie automatically deduplicates and uses the content only once.” |
| Guidelines files from other agents (Claude Code, Codex, Cursor) are picked up automatically. | ❌ FALSE | Junie detects them on first open and will “suggest importing the instructions into `.junie/AGENTS.md`” — import is a suggestion (`/import`), not silent loading. |
| Junie’s settings live in one `~/.junie/settings.json` that wins over config files. | ❌ FALSE | `config.json` (user + project) is the documented config file with CLI > project > user precedence; `settings.json` is “a separate channel and … not part of this config.json merge” — “There is no single global precedence across both channels.” |
| Environment variables override command-line flags in Junie. | ❌ FALSE | “For settings that exist as both environment variables and command-line flags, command-line flags take priority.” |
| CI runners must pre-seed a trust marker before Junie will load project config. | ❌ FALSE | “Non-interactive JSON, ACP, and Gateway launches are always trusted: they cannot ask you for a decision, so they load project configuration without a prompt, a flag, or an environment variable.” |
| Untrusted projects block Junie from reading files. | ❌ FALSE | An untrusted project “remains the workspace for ordinary file operations” — what is withheld is project config, MCP, hooks, extensions, models, plans, demos, agents, commands, skills, guidelines, memory, and migration sources, served from “a writable temporary project Junie directory outside the repository.” |
| Trust decisions are stored in `settings.json` (or the plaintext fallback). | ❌ FALSE | Markers live under `<Junie Home>/trust` and “cannot grant trust unless its integrity code matches that key,” an authentication key in macOS Keychain / Windows Credential Manager / Linux Secret Service — “Neither the key nor trust markers are written to settings.json or the plaintext secure_credentials.json fallback.” |
| Hooks can ship in the project’s `.junie/config.json` for the whole team. | ❌ FALSE | “Project-local hooks from `<project-root>/.junie/config.json` are ignored by default for safety” — only user config or an explicit `--config-location` file contributes hooks, and skipped project hooks are reported as a configuration warning. |
| A failed hook aborts the action it guards. | ❌ FALSE | Default is fail-open: “Other non-zero exit codes are logged as a warning and the tool proceeds normally by default”; only exit code 2 blocks, and `blockOnError: true` (sync PreToolUse and Stop only) promotes other failures to blocks. |
| A PreToolUse hook can run async and still block the tool call. | ❌ FALSE | Async hooks “cannot block or affect the triggering action” — “by the time the hook finishes, the action it would have controlled has already happened”; decisions are “logged and ignored.” |
| Stop hooks can block the agent’s submission forever. | ❌ FALSE | “The agent stops dispatching the Stop hook after 8 consecutive blocks within the same task and a system message is published” — overridable with `JUNIE_STOP_HOOK_BLOCK_CAP` (0 disables the cap). |
| StopFailure hooks can retry or abort the agent on provider errors. | ❌ FALSE | “StopFailure is observability-only: it has no decision control. Output and exit code from the hook process are ignored” — `decision: block` and `continue: false` are “demoted to TUI failure notifications.” |
| A PermissionRequest hook failure blocks the action. | ❌ FALSE | Exit 0 auto-approves and exit 2/block auto-denies, but “If no hook matches, or a hook fails with a non-zero exit (other than 2), Junie falls back to showing the normal permission dialog.” |
| SessionEnd hooks can keep the session alive. | ❌ FALSE | “SessionEnd hooks cannot block session termination, even if they return a non-zero exit code or decision: block in their stdout,” and dispatch is capped at a 10-second total budget. |
| Junie hooks use a proprietary wire format incompatible with Claude Code scripts. | ❌ FALSE | PreToolUse/PostToolUse use `decision`/`tool_input`-style JSON with exit-2 blocking, and “The field names match Claude Code’s StopFailure wire protocol, so the same hook script can be shared between agents” (the config format itself is Junie’s). |
| Sandbox mode isolates everything the agent touches, including MCP servers and hooks. | ❌ FALSE | “MCP servers, hooks, and operations performed directly by Junie CLI outside those tools are not isolated by this sandbox… It is not hardened isolation like a container or VM.” |
| The sandbox blocks network access by default. | ❌ FALSE | “Network access is unrestricted by default: agent commands reach the network directly”; filtering requires `"unrestricted": false` plus `allowedDomains` in `~/.junie/sandbox.json`. |
| A cloned repository can loosen its own sandbox via `.junie/sandbox.json`. | ❌ FALSE | “Only the global `~/.junie/sandbox.json` is used; a project-local `.junie/sandbox.json` is ignored (with a warning), so a cloned repository cannot widen its own sandbox.” |
| Brave mode On bypasses the sandbox policy. | ❌ FALSE | Brave preference is kept separately for sandboxed sessions, and the policy-file edit flow states: “Your request alone is not approval; brave mode and saved approvals cannot bypass this confirmation.” |
| The sandbox’s mandatory protections can be allowlisted in `~/.junie/sandbox.json`. | ❌ FALSE | “srt also applies its own mandatory write protections that Junie cannot allowlist, notably .git/hooks, .git/config, shell rc files, .mcp.json, and .vscode / .idea directories.” |
| The sandbox makes `~/.ssh` completely unreadable. | ❌ FALSE | It is on the deny-read list “apart from config and known_hosts” so ssh can resolve hosts and verify fingerprints; git authenticates through an ssh-agent without reading keys. |
| Git operations fail under the sandbox in linked worktrees and submodules. | ❌ FALSE | “Junie asks git where its directories are and automatically allows them after verifying that the external metadata belongs to the current worktree” — and you can deny-list `${GIT_DIR}`/`${GIT_COMMON_DIR}` if you disagree. |
| The sandbox reports every blocked operation. | ❌ FALSE | “This is diagnostic monitoring, not a complete audit: denied reads, direct network attempts, unrecognized syscalls, and some ambiguous or truncated paths are not covered… An empty report does not prove that nothing was blocked.” |
| `junie-sandbox-setup.sh` gives Junie administrator rights. | ❌ FALSE | It grants `/usr/bin/bwrap` permission to create user namespaces — “Junie still runs as your normal user. It does not disable AppArmor globally, download code, install packages, or overwrite existing administrator policy.” |
| Junie requires a JetBrains AI subscription to run. | ❌ FALSE | BYOK works “on its own or together with JetBrains Account authorization,” and custom models or proxies need no subscription at all. |
| With both a subscription and BYOK connected, usage is billed to JetBrains first. | ❌ FALSE | “If a model is available through both your BYOK key and your JetBrains subscription, the BYOK key takes priority, and the requests are billed to your provider.” |
| Model aliases always track the latest model versions. | ❌ FALSE | Each alias “maps to a specific model version set by the JetBrains team… and is not necessarily the latest available version. The model behind each alias may change as new models are released.” |
| The internal helper tasks reuse the model you selected. | ❌ FALSE | “Junie also uses a separate model for certain internal tasks” picked from the same provider — “This applies even when using BYOK… you may see API calls to a model you didn’t explicitly select.” |
| `--effort` can be used on its own. | ❌ FALSE | The flag “Requires `--model`, `JUNIE_MODEL`, or `--agent`” — unsupported values fall back to the model default. |
| An explicit `--model` for a premium JetBrains model works on a Junie-Lite-only account. | ❌ FALSE | “An explicit `--model` request for a premium JetBrains model fails with an access message when only Junie Lite is available. Specify `--provider` to use the same model through another available provider.” |
| Custom model profiles must hardcode API keys. | ❌ FALSE | `apiKey` and `extraHeaders` values support `${VAR_NAME}` environment references; an unset variable means “the profile fails to load and Junie reports an error identifying the missing variable.” |
| `extraBody` fields cannot override the fields Junie sets. | ❌ FALSE | “If a key conflicts with a field Junie already sets (for example, `model` or `messages`), the extraBody value takes precedence, so use it with care.” |
| Junie sends `temperature: 0` for custom models by default. | ❌ FALSE | “Junie does not send a temperature value for custom models, allowing the provider to use its own default.” |
| Proxy endpoints can be defined with CLI flags. | ❌ FALSE | “Proxy configuration is only available through config.json. There are no dedicated CLI flags for defining proxy entries.” |
| The OpenRouter proxy kind is supported for routing. | ❌ FALSE | The `OpenRouter` and `JetBrainsAI` proxy kinds are “reserved for future use — selecting it as the active provider fails”; OpenRouter is a BYOK provider, not a proxy kind. |
| Merged config files combine `available-models` proxy lists. | ❌ FALSE | “available-models is replaced, not combined — otherwise a lower-priority file could widen a list the higher-priority one deliberately narrowed.” |
| Junie Local runs any local model via Docker on any machine. | ❌ FALSE | It is a bundled inference engine for macOS 26+ on Apple Silicon (M4 or newer) with 48 GB of RAM or more, and Windows 11 with an Ampere-or-newer NVIDIA RTX GPU and 24 GB of VRAM or more — no Docker, and it installs 4-bit quantized Qwen3.6-27B / Qwen3.8-3.6-27B-blend builds, not the full-weight models. |
| Junie Local serves the full-weight open models. | ❌ FALSE | “Junie Local does not download those: it installs 4-bit quantized builds of them” — MLX 4-bit on macOS, Q4_K_M GGUF on Windows. |
| Junie Lite has a published quota. | ❌ FALSE | “Junie Lite does not publish a quota number” — “Virtually unlimited describes normal use”; at capacity “requests stop rather than falling back to another model — there is no downgrade path.” |
| Junie Lite is available inside JetBrains AI Assistant. | ❌ FALSE | “Junie Lite is not available inside JetBrains AI Assistant” — it ships in JetBrains Air and Junie CLI. |
| Junie Lite is a trial tier. | ❌ FALSE | “It is not a trial, not a limited-time sample, and it does not expire or count down”; the underlying model (currently Qwen 3.6 27B) may change “without notice.” |
| Eco mode is a separate cheaper model you configure. | ❌ FALSE | “It is a run mode on top of the model you selected”: planning stays on the selected model and implementation moves to “a cheaper implementation model” that Junie itself chooses from the same provider route. |
| Eco mode applies to headless and CI runs. | ❌ FALSE | “Headless / CI runs: Eco mode is not included outside interactive and ACP sessions,” and a `/remote` bridge prompt “does not run under Eco mode.” |
| GitHub Copilot BYOK needs a personal access token. | ❌ FALSE | “GitHub Copilot authenticates through the GitHub Copilot CLI installed on your machine — Junie CLI reuses its sign-in” (Copilot CLI ≥ 1.0.65), and models must be enabled in the Copilot settings on github.com. |
| `--agent` sessions also run in Chat mode. | ❌ FALSE | “Classic session mode: `--agent` locks the session to Classic mode and cannot be combined with `--agent-mode chat`” (built-in workflows still route to their handlers). |
| Custom subagents can be invoked via slash commands. | ❌ FALSE | “Unlike custom slash commands, custom subagents cannot be invoked manually via slash commands” — delegation is automatic, or `--agent <name>` runs one standalone. |
| Subagents always get cheaper models. | ❌ FALSE | The EAP policy is a choice: `SameModelOnly` keeps the main model; `Auto` (default) “may choose cheaper capable model tiers for suitable delegated work when it does not slow the session.” |
| Skills are loaded fully into every prompt. | ❌ FALSE | Progressive disclosure: “each skill’s name and description are available to Junie, so it knows what skills exist, but doesn’t read the full content of a skill until it determines its relevance.” |
| A skill without a `description` fails to load. | ❌ FALSE | “If description is not provided in the frontmatter, Junie CLI extracts the first paragraph of the body content as the description” — only an empty body fails the load. |
| Disabled skills still influence Junie. | ❌ FALSE | They are “excluded from automatic selection, from the `/<skill-name>` commands, and from the `$` suggestions, and their instructions are not added to Junie’s context”; the choice persists across sessions. |
| Custom slash commands accept free-form text by default. | ❌ FALSE | “By default, custom slash commands accept only the named arguments defined in the command template”; `allowPromptArgument: true` adds the `$prompt` argument. |
| MCP request timeouts are fixed at 60 seconds. | ❌ FALSE | A per-server `timeout` field (milliseconds, 1,000–3,600,000) overrides the 60-second default; out-of-range values are ignored with a warning — and `"timeout": 60` is “rejected instead of being treated as one minute.” |
| Junie invented its own MCP config schema. | ✅ TRUE | The docs state plainly: “Junie CLI uses the same MCP JSON configuration as Junie in JetBrains IDEs” — a standard `mcpServers` object in `mcp.json`. |
| The extensions system only accepts JetBrains-native manifests. | ❌ FALSE | “Two manifest formats are supported”: native `.junie-extension/marketplace.json` and “the Claude plugin format at `.claude-plugin/marketplace.json`” — “you can connect any Claude-compatible plugin marketplace to Junie CLI.” |
| The IDE Action Allowlist can allow specific MCP servers or tools. | ❌ FALSE | “Adding an item of the MCP Rule type … will authorize Junie to run all MCP tools without user confirmation. Defining the specific MCP servers and tools … is not possible yet” (the CLI’s `mcpTools` rules do support per-server prefixes). |
| `ls`, `cd`, and `pwd` need approval in the IDE. | ❌ FALSE | “The `ls`, `cd`, and `pwd` terminal commands with any arguments are executed without user confirmation by default. However, combining commands like `cd .. && ls` will require confirmation.” |
| An allowlist rule for `git` covers `git status && curl …`. | ❌ FALSE | “A rule allows a terminal command only when every command it runs is allowed” — chains are checked part by part, substitutions “at any nesting depth,” and “a command that spans several lines always asks for approval.” |
| `.aihide`/`.aiignore` hides file names from Junie. | ❌ FALSE | “Only the contents of files listed in .aiignore are protected. Junie will still have access to the file and folder names,” and Brave Mode or allowlisted commands can still reach them. |
| Plan mode stays on until switched off. | ❌ FALSE | “Plan mode applies to the next prompt you submit. After each submitted prompt, Junie CLI returns to the default mode.” |
| Closing a plan deletes the plan file. | ❌ FALSE | `/plan close` “returns to Default, and keeps the saved plan file. An unchanged closed plan stays inactive.” |
| `/new` ends the current session. | ❌ FALSE | “Use /new to start another live session… Existing live sessions keep running in the background”; on a switch “the outgoing session is not terminated — it continues running in the background, so its SessionEnd hook is not dispatched.” |
| Parallel sessions isolate file changes. | ❌ FALSE | “Parallel sessions share the file system of the project or worktree they are running in. When you want several sessions to make code changes at the same time, use Git worktrees.” |
| Junie worktrees are created inside the project directory. | ❌ FALSE | “Worktree directories are created as siblings of the project directory, for example ../my-project-junie-wt-01. Make sure the parent directory is writable.” |
| Creating a worktree discards uncommitted changes. | ❌ FALSE | Junie asks to transfer them via `git stash` or start clean; a conflicted stash “is left… so you can resolve them manually.” |
| The review agent can fix the code it reviews. | ❌ FALSE | It “uses a more focused system prompt and a subset of read-only tools… it never edits files, runs builds or tests, creates files, or commits and pushes changes.” |
| The GitHub Action runs Junie on JetBrains infrastructure. | ❌ FALSE | “The action executes entirely on your GitHub runners, so your code always stays on your infrastructure.” |
| `pull-requests: write` is enough for the Action to open PRs. | ❌ FALSE | The repository must also enable “the Allow GitHub Actions to create and approve pull requests checkbox enabled in the Workflow permissions section of your repository’s Settings → Actions → General” — “With this setting disabled, the Junie GitHub action will not be able to create PRs, even with the pull-requests: write permission in the workflow.” |
| `junie_api_key` and a BYOK key can be combined in the Action. | ❌ FALSE | “Provide either junie_api_key or one of the BYOK keys — not both. All API keys are automatically masked in workflow logs.” |
| The inline-comment MCP server must be enabled manually. | ❌ FALSE | “The mcp_github_inline_comment_server is enabled automatically for pull_request events. No manual configuration is needed.” |
| The built-in `code-review` prompt lets the agent modify the PR. | ❌ FALSE | The published prompt instructs: “You may open files or search the project to understand context. Do NOT run tests, build, or make any modifications” and “Do NOT call ‘submit’,” commenting “ONLY on lines added in this diff (`+` lines).” |
| The secrets-audit workflow posts its findings as PR comments. | ❌ FALSE | “It runs in silent mode (`silent_mode: true`), so it doesn’t output any GitHub comments or code changes. Instead, it fails the CI build if sensitive data in commits are found.” |
| GitLab Junie pipelines run inside your existing project’s CI config. | ❌ FALSE | “The setup process requires creation of a separate container project for Junie’s CI/CD pipelines (one per GitLab instance). This allows you to run Junie without tweaking the CI/CD pipelines in your existing projects.” |
| Remote mode works with a BYOK key alone. | ❌ FALSE | “Remote mode requires a Junie subscription… Bring Your Own Key (BYOK) on its own is not enough”; it is also “not available when Junie CLI is signed in through JetBrains AI Enterprise.” |
| Multiple browser tabs can watch the same remote session. | ❌ FALSE | “Only one web client can be connected to a remote session at a time. Opening the URL from another tab or device takes over the connection.” |
| Debug mode works against any debugger directly. | ❌ FALSE | It operates “against a live debugger session connected to a JetBrains IDE”; without one, “Junie CLI reports that ‘Debug mode requires an IDE with debugging support connected’ and stays in the default mode.” |
| Junie CLI’s IDE integration connects to VS Code and other editors. | ❌ FALSE | “Junie CLI currently supports only JetBrains IDEs for this integration. It does not connect to non-JetBrains editors or IDEs” — ACP is the offered path for other editors. |
| The Junie IDE plugin supports BYOK and model selection. | ❌ FALSE | “Using your own API key with Junie is not supported via Junie plugin, however, you can do so in AI Assistant’s AI chat in your JetBrains IDE”; the plugin’s Ollama/`/account` support is likewise absent (“Command ‘account’ is not supported”). |
| You must manually install the Junie IDE plugin to use Junie in a JetBrains IDE. | ❌ FALSE | The recommended surface is the single AI Chat, where Junie is “downloaded automatically”; the manual plugin install is “required only if you want to use Junie from a separate tool window.” |
| `/demo` runs the app on your host machine. | ❌ FALSE | “The demo VM is a Docker container” layered on `registry.jetbrains.team/p/junie-cli/containers/demo-base:2` — `/demo` “will not start without a working Docker daemon” and needs a Computer-Use-capable model. |
| `/usage` is the only cost command. | ❌ FALSE | `/stats` is the primary command with aliases “`/usage`, `/cost`, `/quota`, `/balance`, `/credits`” — same data (session and all-time token usage, costs, models). |
| Cache cleanup deletes old sessions along with everything else. | ❌ FALSE | “Saved sessions are your data, not cache. Junie CLI never deletes them unless you explicitly ask for it with `--sessions` or enable the cacheAutoPruneSessions setting” — and only finished sessions older than 90 days, never ones open in a running process. |
| Automatic cache pruning runs in headless mode. | ❌ FALSE | “Automatic pruning works only for Junie CLI installed with the install script and with auto-updates enabled. It does not run in headless mode.” |
| `/quit` signs you out. | ❌ FALSE | “To exit the Junie CLI interactive mode without losing login credentials, use `/quit`” — sign-out is a separate action on the account screen (with its own `logout` SessionEnd reason). |
| Junie CLI is generally available. | ❌ FALSE | The headless page carries the banner “Junie CLI is currently in an Early Access Program (EAP),” and sandbox mode, hooks, the subagents setting, and custom proxies are each EAP-flagged in their own docs. |
| Junie is Claude Code compatible. | ⚠️ PARTIAL | Real compat surface: Claude-Code-shaped hook JSON (`decision`/`tool_input`, exit 2 = block), the StopFailure wire protocol (“the same hook script can be shared between agents”), Claude-plugin marketplace manifests and `hooks/hooks.json` with `${CLAUDE_PLUGIN_ROOT}`, plus import detection for `.claude/`, `.codex/`, and `.cursor/` assets — but the config format, settings channels, and approval model are Junie’s own. |
| Junie CLI is fully cross-platform. | ⚠️ PARTIAL | The CLI installs on “Linux, macOS, and Windows,” but sandbox mode “is not available on Windows,” Junie Local splits by platform (Apple Silicon vs NVIDIA RTX), and trust storage uses a different secure store per OS. |
| The Junie registry identity covers one product. | ⚠️ PARTIAL | “Junie” spans the CLI, the IDE plugin/AI Chat surface, the GitHub Action, GitLab CI/CD, and Junie Local/Lite/Eco — with materially different capability sets per surface (e.g. BYOK and Ollama are CLI-only; RunTest/Build/Preview allowlist rules are IDE-only). |
| Junie Local’s blend model is the better local choice. | 💬 OPINION | JetBrains’s own benchmark claim (“completes more coding tasks than Qwen3.6 while generating far fewer output tokens than Qwen3.8”) is the only support for preferring Qwen3.8-3.6-27B-blend; the docs do not mandate it. |
| The MCP `mcp.json` format is shared with the IDE plugin. | ✅ TRUE | “Junie CLI uses the same MCP JSON configuration as Junie in JetBrains IDEs” — the same `mcpServers` JSON loads at project and user scope for both. |
