# Hermes Agent corrections log

**Verified:** 2026-11-15

| Claim | Verdict | Correction |
|---|---|---|
| Hermes Agent runs only Nous Research’s own Hermes models. | ❌ FALSE | The provider registry spans “openrouter, nous, openai-codex, anthropic, gemini, qwen-oauth, zai, kimi-coding, minimax-oauth, deepseek, xai-oauth, ollama-cloud, bedrock, azure-foundry” plus a `custom providers` dict, with a universal provider/model/base_url pattern; Nous Portal (`hermes setup --portal`) is the convenience path, not a requirement. |
| Hermes Agent is a coding copilot that lives in the IDE. | ❌ FALSE | The overview positions it as “not a coding copilot” but a “self-improving AI agent” — a terminal-native CLI/TUI/desktop product. Editor integration is outbound via ACP (`hermes acp`) or the embedded `hermes mcp serve`, not an IDE extension. |
| Configuration lives in `~/.config/hermes/` as JSON. | ❌ FALSE | Settings are YAML under `~/.hermes/` (`config.yaml`) with `.env` for credentials; `$HERMES_HOME` relocates the whole home, and named profiles live in `~/.hermes/profiles/<name>/`. |
| The only way to change settings is editing `config.yaml` by hand. | ❌ FALSE | `hermes config set` routes UPPER_SNAKE keys to `.env` and dotted keys to `config.yaml`; `hermes setup` is interactive, and `hermes config migrate` prompts for unconfigured skill settings. |
| Provider API keys belong in `config.yaml`. | ❌ FALSE | Keys live in `~/.hermes/.env` (or external secret sources — Bitwarden, 1Password, or a command helper); `config.yaml` holds provider/model references, and every injected credential is “labelled with its origin”. |
| Shell environment variables always outrank config-file values. | ❌ FALSE | Managed scope “deliberately wins over the shell environment too” for the keys it pins; general precedence is CLI args > `config.yaml` > `.env` > built-in defaults. |
| Hermes runs YOLO by default and has no approval system. | ❌ FALSE | Approval modes are `smart`/`manual`/`off` with prompted, smart-classified, or skipped decisions; YOLO is opt-in (`--yolo`, `/yolo`, `HERMES_YOLO_MODE`), a hardline blocklist stays as a floor, and `approvals.deny` user globs “are evaluated before YOLO”. |
| `/yolo` disables every safety check. | ❌ FALSE | YOLO skips dangerous-command approval prompts, but the hardline blocklist remains a floor and user `approvals.deny` globs are still evaluated first. |
| Approvals cannot be answered from a messaging platform. | ❌ FALSE | Gateway platforms get approval prompts and buttons, plus `/approve [session\|always]` and `/deny`; smart mode decides without a human, and prompts time out after `approvals.timeout` (default 300 s). |
| Memory auto-compacts when the character limit is hit. | ❌ FALSE | “Memory does **not** auto-compact: when a write would exceed the limit, the `memory` tool returns an error” and the agent must consolidate or remove entries in the same batch. |
| A memory saved mid-session updates the running system prompt. | ❌ FALSE | Memory is injected “as a frozen snapshot” at session start — writes persist to disk immediately but “won’t appear in the system prompt until the next session starts”. |
| `SOUL.md` is discovered from the project working directory. | ❌ FALSE | “Hermes loads `SOUL.md` only from `HERMES_HOME`” and “does not probe the working directory for `SOUL.md`”; project context comes from the `.hermes.md`/`AGENTS.md` family instead. |
| Hermes stacks `.hermes.md`, `AGENTS.md`, `CLAUDE.md`, and `.cursorrules` together. | ❌ FALSE | “Only **one** project context type is loaded per session, first match wins”: `.hermes.md` → `AGENTS.override.md` → `AGENTS.md` → `CLAUDE.md` → `.cursorrules`. `SOUL.md` is loaded independently as identity. |
| Editing `AGENTS.md` or memory mid-session changes the running prompt. | ❌ FALSE | “Context is assembled at session start, so restart the session to pick up changes”; the same applies to `SOUL.md` edits while a session is running. |
| Skills found in a cloned repo load automatically. | ❌ FALSE | “Hermes does **not** auto-load them from arbitrary cloned repos” — a banner asks for `hermes skills trust`, trust is stored in `skills.trusted_project_dirs`, and a dangerous scan verdict quarantines the skill. |
| Skills Hub `--force` overrides any scan verdict. | ❌ FALSE | “`--force` can override policy blocks for caution/warn-style findings” but “does **not** override a `dangerous` scan verdict”. |
| Hermes uses a proprietary skill format. | ❌ FALSE | Skills are “compatible with the agentskills.io open standard” — a `SKILL.md` with standard frontmatter, plus `references/`, `templates/`, `scripts/`, `assets/`. |
| The full content of every installed skill rides in every prompt. | ❌ FALSE | Loading is progressive: `skills_list()` returns a ~3k-token index, and `skill_view(name)` loads full content only when needed (with `skill_view(name, path)` for reference files). |
| Gateway hooks prompt for consent the first time they run. | ❌ FALSE | The hooks directory is “trusted-by-placement” — “Dropping the two files into the directory **is** the opt-in”; there is no enable list, no first-use prompt, and `HERMES_SAFE_MODE` does not skip the loader. |
| A failed shell hook aborts the tool call. | ❌ FALSE | Shell hooks “fail open” by default — a spawn error, timeout, or unparseable stdout logs a warning and the action proceeds; `fail_closed: true` (pre_tool_call only) inverts that, and exit code 2 blocks. |
| Hooks use Claude Code’s event names (`PreToolUse`, `PostToolUse`, `Stop`). | ❌ FALSE | The hook catalog uses `pre_tool_call`, `post_tool_call`, `pre_llm_call`, `subagent_stop`, and friends; `pre_llm_call` covers `UserPromptSubmit` (“intentionally not a separate Hermes event”). Shell hooks do accept Claude-Code-compatible JSON shapes (`decision`/`tool_input`, exit 2 = block). |
| Cron is a wrapper around the system crontab. | ❌ FALSE | “Cron execution is handled by the gateway daemon” — it ticks every 60 s over `~/.hermes/cron/jobs.json`. `hermes cron tick` exists for external schedulers, but “the gateway must be running” for agent jobs. |
| A scheduled agent can schedule more cron jobs by default. | ❌ FALSE | “Hermes disables cron management tools inside cron executions to prevent runaway scheduling loops”; opting in takes `cron.allow_agent_scheduling: true`. |
| Sessions are stored as JSON transcript files. | ❌ FALSE | Sessions live in SQLite — `~/.hermes/state.db` with WAL and FTS5 full-text search; per-platform transcript files exist only alongside for some messaging adapters. |
| Checkpoints are always recording. | ❌ FALSE | “Checkpoints are opt-in as of v2 — most users never use /rollback”; enable with `hermes chat --checkpoints` or `checkpoints: enabled: true`. |
| `/rollback` only rewinds the conversation. | ❌ FALSE | It restores files — default restore keeps hand-edits, `--all` overwrites them too, and it “also undoes last chat turn”. (`/undo`, by contrast, “only rewinds the conversation; it never touches files”.) |
| The Docker terminal backend starts a fresh container per command. | ❌ FALSE | “Hermes starts a single long-lived container … and routes every terminal, file, and `execute_code` call through `docker exec` into that same container”; `container_persistent: true` keeps `/workspace` across restarts. |
| Docker containers run with all Linux capabilities dropped. | ❌ FALSE | The base flags are `--cap-drop ALL` immediately followed by `--cap-add DAC_OVERRIDE` (“Root can write to bind-mounted dirs”), `--cap-add CHOWN`, and `--cap-add FOWNER` (“Package managers need file ownership”); `SETUID`/`SETGID` join “conditionally when the container starts as root and an init/entrypoint must drop privileges (the s6 privilege-drop path)” and are skipped for non-root `--user` containers. |
| MCP tools are namespaced `mcp__server__tool`. | ❌ FALSE | Hermes prefixes MCP tools as `mcp_<server_name>_<tool_name>` (single underscores) — e.g. `mcp_filesystem_read_file`. |
| MCP tools run in parallel by default. | ❌ FALSE | “By default, MCP tools run sequentially — one at a time”; concurrency needs `supports_parallel_tool_calls: true` per server. |
| MCP config lives in a separate `mcp.json`. | ❌ FALSE | Servers are configured under `mcp_servers` in `~/.hermes/config.yaml`; the running gateway watches that file (tears down removed entries within about a minute), and `/reload-mcp` re-probes on demand. |
| Managed scope locks the entire configuration. | ❌ FALSE | It “injects specific immutable values on a per-key basis” — “Everything else stays fully user-controlled” — and v1 enforcement “is filesystem permissions only … a management-convenience boundary against a normal user, not an un-escapable sandbox”. |
| The managed `.env` is the right place for high-sensitivity secrets. | ❌ FALSE | The managed `.env` is world-readable (0644) — “Use it for shared, non-sensitive values … rather than high-sensitivity secrets”. |
| External secret managers always override values already in `.env`. | ❌ FALSE | “Your .env / shell wins by default”; a source replaces an existing value only with `override_existing: true`, “first source wins” on conflicts, and `secrets.preserve_existing` pins vars against any override. |
| Cron scripts inherit the agent’s provider API keys. | ❌ FALSE | Script subprocess environments are sanitized — only `terminal.env_passthrough` names (or a skill’s `required_environment_variables`) are forwarded, and “Hermes-managed provider credentials … cannot be declared”. |
| Cron prompts must tell the agent where to send output. | ❌ FALSE | “The agent’s final response is automatically delivered to the configured `deliver:` target — the agent does not send messages itself”, with fan-out (`all`, comma lists) resolved at fire time. |
| Cron jobs share one session and remember previous runs. | ❌ FALSE | “Cron jobs run in isolated sessions with no memory of previous runs”; `context_from` chaining and `continuity=true` are opt-in mechanisms. |
| ACP clients are passive; permission prompts can’t be answered from the editor. | ❌ FALSE | ACP approvals offer “allow once, allow for session, allow always, deny”, and “on timeout or error the bridge denies” (fail closed). |
| `hermes chat` runs the agent inside your terminal process. | ❌ FALSE | The classic CLI “no longer runs the agent inside your terminal process” — it attaches to the profile’s gateway over WebSocket; closing the terminal detaches and “accepted work continues at the gateway”. |
| Bot Mode is a separate product you install. | ❌ FALSE | “Bot Mode ships built into the desktop app and is on by default”, and “a Bot **is** a Hermes profile” — a UI over `~/.hermes/profiles/<name>/`. |
| In a group chat every bot replies to every message. | ❌ FALSE | “Speaking is each member’s own choice — a Bot replies only when it has something new to add and passes otherwise”; @-mentions scope the round, and hard caps (10 messages per send, 3 rounds) bound the discussion. |
| Delegated subagents can prompt for a sudo password. | ❌ FALSE | “Delegated subagents cannot open a password prompt: their concurrent work does not have a serialized human password channel” — run sudo in the parent or provision `SUDO_PASSWORD`. |
| Messaging chats auto-reset daily like the CLI. | ❌ FALSE | On messaging platforms “a chat is deliberately one continuous session that survives restarts, gateway crashes, and machine reboots” — `/new` at natural boundaries is the operator’s job; auto-prune is off by default (`retention_days: 90` applies only when enabled). |
| Session search summarizes past conversations with an LLM. | ❌ FALSE | `session_search` queries the SQLite FTS5 index and “return[s] actual messages from the DB — no LLM summarization, no truncation”. |
| Hermes requires a Nous Portal subscription. | ❌ FALSE | Any registry provider works with its own credentials; the Portal is the low-friction path (`hermes setup --portal`) and the Tool Gateway (web search, image gen, TTS, browser) is the subscriber convenience layer. |
| Hermes cannot import Claude Code configuration. | ❌ FALSE | `hermes import-agent claude-code` migrates the `mcpServers` block (to `mcp_servers`), skills, and instructions automatically. |
| `hermes --tui` is an experimental add-on. | ❌ FALSE | The TUI ships with the product — “Launch it with `hermes --tui`” — with modal overlays, mouse selection, and non-blocking input. |
| Hermes runs only on macOS and Linux. | ❌ FALSE | The docs ship Windows (native) and Windows (WSL2) guides, and the overview documents a PowerShell install (`irm …/install.ps1 \| iex`) plus Termux, Nix, and Docker paths. |
| Scheduled watchdogs can run with zero LLM involvement. | ✅ TRUE | No-agent cron jobs deliver script stdout directly — “No tokens, no model, no provider fallback — the job never touches the inference layer”, with empty stdout a silent tick. |
| The documentation publishes a machine-readable index. | ✅ TRUE | The docs site serves `/llms.txt` and `/llms-full.txt` machine-readable indexes alongside the human pages. |
| Hermes is Claude Code compatible. | ⚠️ PARTIAL | Real compat surface: `CLAUDE.md` context files, Claude-Code JSON hook shapes (exit 2 = block, `decision`/`tool_input`), `hermes import-agent claude-code`, and the `mcpServers` mapping — but event names, config format, and the approval model are Hermes’s own. |
| Hermes Agent is a coding agent. | ⚠️ PARTIAL | Coding workflows are first-class (`/plan` writes to `.hermes/plans/`, the `pre_verify` gate, checkpoints, worktrees, `/init` AGENTS.md generation) — but the docs position it as a general-purpose autonomous agent, with 20+ messaging platforms, cron, and Bot Mode as equal citizens. |
| Bot Mode group chats are the recommended way to run multi-agent work. | 💬 OPINION | The docs describe group chats, `delegate_task` subagents, Kanban boards, and chained cron jobs as parallel capabilities; no page states a preference among them. |
