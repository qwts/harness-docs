# Warp corrections log

**Verified:** 2026-11-16 (Warp docs `warpdotdev/docs` main, changelog 2026.11.05 / app v0.2026.11.04.08.17; Warp Agent CLI quickstart/reference current; `warpdotdev/warp` AGPL-3.0)

| Claim | Verdict | Correction |
|---|---|---|
| Warp is just an AI-powered terminal. | ⚠️ PARTIAL | The terminal is one surface of “an **Agentic Development Environment**”: the app, the Warp Agent (“It works in a real terminal”), the Warp Agent CLI, cloud agents on the Automation Platform, and Warp Factories. The product “born out of the terminal” (warpdotdev/warp) has grown past it. |
| Warp is closed-source, as it famously was. | ❌ FALSE | “Warp is an **Agentic Development Environment**” — the main repo `warpdotdev/warp` is public under AGPL-3.0, and docs issues/PRs run through it. |
| You need the Warp app to use the Warp Agent. | ❌ FALSE | “The CLI doesn't require the Warp app to be installed.” The Warp Agent CLI “works in any terminal emulator, including over SSH,” and cloud agents run without any local install. |
| The Warp Agent CLI is the `warp-cli` command. | ❌ FALSE | `warp-cli` is the *old* name of the cloud-management CLI: the legacy “`oz` binary, which previously shipped as `warp-cli`,” is “a supported legacy interface” for cloud agents. Today's `warp` binary is the Warp Agent CLI — a different tool for local agent conversations. |
| The agent's commands run inside a sandbox. | ❌ FALSE | Locally the agent runs “shell commands, reads live output, and drives interactive programs like REPLs, database shells, and full-screen apps” — a real terminal/PTY, unsandboxed. Sandboxing appears in Computer Use (“only available in Warp's sandboxed cloud environments”) and cloud-run environments, not local runs. |
| Auto-approve still enforces your command denylist. | ❌ FALSE | “With auto-approve on, the agent runs commands and applies file edits without review, including commands that match your own command denylist.” Set `auto_approve_bypasses_command_denylist = false` to keep it; only team denylists from the Admin Panel “always require approval and are never bypassed.” |
| `agent_decides` lets the agent auto-apply file edits. | ❌ FALSE | “For **Apply code diffs**, `Agent decides` currently behaves the same as `Always ask` — the Agent always prompts you to review diffs before applying them. Only `Always allow` skips the review prompt.” |
| BYOK provider keys are stored on Warp's servers. | ❌ FALSE | “Warp never stores provider keys on its servers.” Keys live in “your device's secure storage,” and “The CLI and Warp app store provider keys separately. Configure a key in each surface you use.” |
| Personal BYOK keys work for cloud runs. | ❌ FALSE | “Personal BYOK keys work for local Warp Agent runs, not cloud runs” — cloud inference needs Warp-provided usage or admin-configured team-managed keys/endpoints (Business/Enterprise). |
| Once BYOK is configured, Auto models bill through your provider. | ❌ FALSE | “Warp's built-in Auto models always use Warp-provided inference, even with BYOK configured.” To bill through your own key you must select a specific provider model or a custom router whose targets your keys cover. |
| Project-scoped MCP servers start automatically. | ❌ FALSE | “Project-scoped servers from any provider require explicit approval,” toggled on individually and session-scoped. Warp “prevents a cloned repo from automatically starting an MCP server that runs arbitrary local commands.” |
| The Warp Agent CLI picks up project-scoped MCP config files. | ❌ FALSE | “The CLI reads MCP servers from its global config file only. Project-scoped MCP config files in repositories are not detected.” Its config lives at `~/.warp_cli/.mcp.json` (macOS), separate from the app's. |
| Agents edit MCP config files silently. | ❌ FALSE | “**Config edits require approval** - Warp prevents edits to MCP config files unless you explicitly approve the change,” so an agent or automation cannot quietly add a server. |
| Warp requires a `WARP.md` rules file. | ⚠️ PARTIAL | “Warp uses `AGENTS.md` as the default project rules file”; `WARP.md` is legacy but wins conflicts: “If both `WARP.md` and `AGENTS.md` exist in the same directory, `WARP.md` takes priority.” Either way, “The filename must be in **all caps** for Warp to recognize it.” |
| CLI settings sync to your Warp account. | ❌ FALSE | “CLI settings are local to your machine and are never synced to the cloud,” and they are “independent from the Warp app's settings: the app and the CLI keep separate settings files.” |
| CLI execution profiles are the same as app Agent Profiles. | ❌ FALSE | “They never sync to the cloud, and they are separate from the Agent Profiles you configure in the Warp app.” You can define more, but “the CLI currently always runs with `default`.” |
| Rules and skills must be migrated into the CLI. | ❌ FALSE | “Rules and skills don't need migration: the CLI and the Warp app both discover them from the same file locations.” Only settings and global MCP servers move, via the bundled `/tui-migrate-setup` skill — “Credentials and OAuth state are never copied.” |
| Third-party CLI agent sessions show up in the Conversation Panel. | ❌ FALSE | “Claude Code, Codex, OpenCode, and other third-party CLI agents do **not** appear there.” They run as panes with vertical-tab status and the agent toolbelt; Remote Control publishes them for monitoring. |
| Cloud child agents can be steered from the CLI. | ❌ FALSE | “Cloud child sessions in the CLI only show status. They don't accept input. To send prompts to a cloud child or respond to its approvals, open the run in the Oz web app.” |
| Any cloud run can be resumed in the CLI. | ❌ FALSE | Two gates: “The run must be finished - Cloud runs that are still in progress or blocked can't be opened in the CLI” and “Warp Agent runs only - Conversations that ran with a different harness, such as Claude Code or Codex, can't be opened in the CLI.” |
| Scheduled agents pick up where the last run left off. | ❌ FALSE | Each run “Starts a fresh agent session for every run” with “a fixed prompt defined at schedule creation time,” on a cron expression, in a specified environment if one is set. |
| Agent Memory is generally available. | ❌ FALSE | “Agent Memory is in **research preview** and is enabled per team for design partners,” with a waitlist. When enabled it is cross-harness: “One memory system is shared across the Warp Agent, Claude Code, Codex, and other harnesses as they're added.” |
| Computer Use works in your local terminal session. | ❌ FALSE | “Computer Use is only available in Warp's sandboxed cloud environments, not in local interactive terminal sessions.” It is “enabled by default for cloud agent runs on Warp's built-in harness” and defaults to disabled on third-party harnesses. |
| Cloud children inherit the parent's secrets, MCP servers, and integrations. | ❌ FALSE | “Do not assume every child inherits the parent's secrets, MCP servers, or integrations,” and “Sharing an environment definition does not mean sharing a running filesystem” — cloud children get explicitly chosen harness, environment, and keys. |
| Handoff moves your local conversation to the cloud. | ⚠️ PARTIAL | “Warp forks the conversation, so the cloud agent sees the full transcript and your local conversation stays untouched.” It also snapshots “your uncommitted repository changes, including untracked files,” and applies them in the cloud run. |
| You can hand off a conversation while a command runs. | ❌ FALSE | “You can't hand off while a command is still running, or while the conversation has child agents that are in progress or blocked. Cancel the command or let the children finish first.” |
| Warp Factories and the Automation Platform are the same product. | ⚠️ PARTIAL | “Warp Factories and standalone cloud agents run on the Automation Platform” — the platform supplies shared execution, configuration, and APIs; Factories is “open, flexible infrastructure for building … your own software factory” on top of it. |
| The Oz CLI is deprecated and no longer supported. | ⚠️ PARTIAL | “The Oz CLI (the `oz` binary, which previously shipped as `warp-cli`) is a supported legacy interface. Existing users do not need to change their workflows. … Warp will publish guidance before any support change.” |
| A Claude subscription can be connected for inference. | ❌ FALSE | “You can't connect a Claude consumer subscription to the Warp Agent.” Anthropic access is BYOK; connectable subscriptions are ChatGPT (eligible OpenAI models) and X Premium/SuperGrok for Grok. |
| Local child agents can run on Claude Code or Codex harnesses. | ❌ FALSE | “Local children always run the Warp Agent.” Only cloud children “can run a different harness than the parent, such as Claude Code or Codex,” chosen on the orchestration approval card. |
| All Warp Drive objects follow you into the CLI. | ⚠️ PARTIAL | “your saved Warp Drive prompts are available after you log in (other Warp Drive object types aren't available in the CLI).” Rules and skills come from the same file locations instead. |
