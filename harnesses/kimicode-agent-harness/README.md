# Kimi Code harness

**Verified:** 2026-11-15 against the official Kimi Code documentation at www.kimi.com/code/docs/en (Moonshot AI)
**Status:** Reference documentation, not a runtime conformance audit
**Primary scope:** `kimi` CLI (`@moonshot-ai/kimi-code`, Node ≥ 22.19; TUI, `-p` print mode, ACP), Desktop app, VS Code extension, `kimi web` browser UI, Remote Control, remote environments, `~/.kimi-code/config.toml` + `tui.toml` configuration, providers and model pool, permission modes and rules, hooks, skills/MCP/plugins, agents/subagents, Tower, Goal/Swarm modes, sessions and cron, Kimi membership and models
**Provenance:** Official Kimi sources unless explicitly marked otherwise

Kimi Code (Moonshot AI) is a multi-surface coding agent built around one Node CLI: a TUI, a non-interactive `-p` print mode with stream-json output, an ACP server for Zed/JetBrains/Paseo, a `kimi web` browser UI, Desktop and VS Code wrappers, and `kimi rc` Remote Control. All surfaces read one TOML config — “runtime settings live in config.toml, and terminal-UI preferences live in a companion tui.toml” — with a strict credential rule (“It does not fall back to shell environment variables automatically”), a three-mode approval model (Always Ask / Ask When Needed / Never Ask) hardened by fixed deny > ask > allow rule precedence, workspace trust gating project-level MCP servers, and user-config-only hooks as a supply-chain guard. Subagents delegate through coder/explore/plan built-ins onto a `[secondary_model]` pool; experimental Tower coordinates mission workers in Git worktrees; Goal mode runs objective-driven loops; sessions store full wire traffic under `~/.kimi-code/sessions/`. The `kimicode` registry identity normalizes to this single harness (distinct from the kilocode/Kilo Code harness).

## Top corrections

- ❌ **“Providers can read API keys from shell environment variables.”** “It does not fall back to shell environment variables automatically: running export KIMI_API_KEY in the terminal does not give any provider its key” — credentials resolve from `api_key`/`api_key_env` (mutually exclusive), the provider `env` sub-table, or OAuth.
- ❌ **“Project-level config.toml is supported.”** “The CLI currently reads a single user-level config file and has no project-level config file mechanism” — project-side exceptions are `.kimi-code/local.toml` permission rules (trusted workspaces only) and project `mcp.json`.
- ❌ **“Permission rules are first-match-wins.”** “Matching deny rules take precedence over matching ask rules, which take precedence over matching allow rules.”
- ❌ **“dangerous_command_guard = false only affects dangerous shell commands.”** It turns “off every built-in guard confirmation policy entirely: dangerous commands, access to sensitive files such as .env or id_rsa, and access to git control paths” — only the “hard block that stops Read/Write/Edit from touching secret files stays in effect.”
- ❌ **“Hooks can be defined per-project.”** “All hook rules are written in the [[hooks]] array in ~/.kimi-code/config.toml” — “there is no project-level hook file, so content checked out on a remote target can never inject hook definitions into your session.”
- ❌ **“K3.1 Pro can run with thinking off.”** “K3.1 Pro models only support thinking mode. Requests with thinking disabled are rejected” — and a mistyped model ID silently “falls back to K2.8 Preview without thinking.”
- ❌ **“The agent can enter Plan mode itself, and Never Ask removes all confirmations.”** “Only you can turn Plan mode on; the agent never enters it on its own,” and “Exiting Plan mode always requires your confirmation, in every permission mode, including Never Ask.”
- ❌ **“Tower workers can spawn subagents, and worktrees are a security sandbox.”** “Tower workers do not have the Agent tool and cannot spawn subagents,” and “Worktrees isolate writes, but they are not a security sandbox. Workers can read repository content and run tools with your permissions” — “Mission scopes and merge checks are process constraints, not security boundaries.”
- ❌ **“Remote commands fall back to local execution.”** “There is no silent fallback to your machine, so a remote command cannot accidentally run locally” — and hooks “always execute on the machine running Kimi Code.”
- ❌ **“HTTP 429 is always retried.”** “A 429 caused by an exhausted quota or insufficient account balance is not retried and fails immediately” — only transient failures retry.

| Goal mode | `/goal` objective ≤ 4000 chars (“what must become true”); complete/paused/blocked; budget “only ticks while the goal is active and the session is open”; `/goal next` queue invisible to agent; non-interactive exits 0/3/6 |
| MCP | `mcp.json` user + project (project wins, trust-gated); stdio/HTTP/legacy SSE; `environment_id` for remote stdio; `bearerTokenEnvVar`, `deferred` (experimental; `select_tools` on-demand), `startupTimeoutMs` 30000; reconnect 5 s→300 s, unrecoverable servers not retried; `mcp__<server>__<tool>`; “In Ask When Needed mode, MCP tool calls are automatically approved” |
