# Qwen Code corrections log

**Verified:** 2026-11-16 (Qwen Code 0.27.4 npm latest; docs site `qwenlm.github.io/qwen-code-docs` main)

| Claim | Verdict | Correction |
|---|---|---|
| Qwen Code is Qwen's LLM. | ❌ FALSE | It is “Qwen's agentic coding tool that lives in your terminal” — an agent harness that connects to models through configured providers; the models are not the harness. |
| Qwen Code only runs Qwen models or requires a Qwen key. | ❌ FALSE | “Supports OpenAI, Anthropic, Gemini, and Qwen APIs. Any third-party provider or local model (Ollama / vLLM). Switch at runtime.” Built-in third-party providers include “DeepSeek, Grok, MiniMax, Z.AI, Kimi, Idealab, ModelScope, OpenRouter, Requesty.” |
| Qwen Code is Gemini CLI with renamed environment variables. | ⚠️ PARTIAL | The fork lineage is real — “Some sandbox-related environment variables may have used the `GEMINI_*` prefix historically. All new environment variables use the `QWEN_*` prefix” — but the current surface goes far beyond the fork point (daemon/Web Shell, channels, Agent Team, arena, SDKs, `qwen serve`, skills, rules). |
| Qwen Code 1.0 is the current release. | ⚠️ PARTIAL | “Qwen Code 1.0 Preview” is a separate preview line (“Try Qwen Code 1.0 Preview” on the `v1.0.0-preview` branch) that “brings together the agent harness capabilities of Qoder and Qwen Code”; the main-line npm latest is 0.27.4, and the docs describe the main version. |
| Folder trust is enabled by default. | ❌ FALSE | “The Trusted Folders feature is **disabled by default**. While it is disabled, every folder counts as trusted, so a project's `.qwen/settings.json` is loaded without any prompt.” |
| With folder trust off, project configuration runs with no prompts at all. | ⚠️ PARTIAL | “Project MCP servers and project hooks still ask for your approval the first time they are seen and whenever they change, unless you run in YOLO mode (for MCP servers, YOLO from any source; for hooks, only `--yolo` or `--approval-mode yolo` on the command line).” |
| API keys can be stored in `settings.json`. | ❌ FALSE | “Credentials are never persisted in settings; the runtime reads them from `process.env[envKey]`.” `security.auth.apiKey`/`baseUrl` are “**Deprecated.** … Migrate to `modelProviders` with `envKey`.” |
| `qwen auth coding-plan` configures the Coding Plan. | ❌ FALSE | The command was removed: “configure Coding Plan with environment variables or `settings.json` instead of the removed `qwen auth coding-plan` command.” |
| Checkpointing is on by default. | ❌ FALSE | “The Checkpointing feature is disabled by default”; enable with `--checkpointing` or `"general": {"checkpointing": {"enabled": true}}`. |
| Auto-memory is opt-in. | ⚠️ PARTIAL | “`memory.enableManagedAutoMemory` … Enable background extraction of memories from conversations” defaults to `true`, as does auto-dream consolidation; the opt-in pieces are `enableAutoSkill` (`false`), `enableTeamMemory` (`false`), and `enableStructuredRecall` (`false`). |
| Scheduled cron tasks persist across restarts. | ❌ FALSE | “Tasks created from the terminal are session-scoped: they live in the current Qwen Code process and are gone when you exit. Nothing is written to disk.” The limitations list confirms “No persistence across restarts. Restarting Qwen Code clears all session-scoped tasks.” |
| Cron scheduling is an experimental opt-in feature. | ⚠️ PARTIAL | Inverted: “`experimental.cron` … Enable in-session cron/loop tools … default `true`”; it is disabled with `experimental.cron: false` or `QWEN_CODE_DISABLE_CRON=1`. |
| `permissions.deny` removes MCP tools from the registry. | ⚠️ PARTIAL | “A whole-tool deny rule … also removes the tool from the registry — for built-in tools and tools found via `tools.discoveryCommand`. MCP tools are exempt …: hide them with the per-server `excludeTools` / `tools.disabled` filters instead. Deny rules still block MCP tool calls at runtime.” |
| A `Read` permission rule covers only `read_file`. | ⚠️ PARTIAL | `Read` is a meta-category — “`Read` | `read_file`, `grep_search`, `glob`, `list_directory`”. To restrict only file reading, “use `ReadFile(/path/**)` or `read_file(/path/**)`.” |
| Shell commands bypass file permission rules. | ❌ FALSE | “Permission rules for `Read`, `Edit`, and `WebFetch` are also enforced when the agent runs equivalent shell commands. For example, if `Read(./.env)` is in `deny`, the agent cannot bypass it via `cat .env` in a shell command.” |
| The Auto-mode classifier replaces permission rules. | ❌ FALSE | “**Hard rules remain in force**: `permissions.deny` rules block actions before the classifier ever runs,” and “Over-broad allow rules are stripped while in Auto Mode” — e.g. `permissions.allow: ["Bash"]` is temporarily disabled so the classifier can judge. |
| The Auto-mode classifier fails open when its API is unreachable. | ❌ FALSE | “**Fail-closed**: when the classifier API is unreachable, the action is blocked rather than allowed. After two consecutive unavailable calls, the next tool call falls back to manual approval.” |
| Hooks are opt-in. | ❌ FALSE | “Hooks are enabled by default. You can temporarily disable all hooks by setting `disableAllHooks` to `true` in your settings file.” |
| Hook matchers are glob patterns. | ❌ FALSE | “`matcher` is a regular expression used to filter trigger conditions.” It is unanchored (`read` matches `read_file`), and pipe-separated lists are exact entries unless the matcher starts with `^` or `(`. |
| YOLO mode exempts project skill/agent frontmatter hooks. | ❌ FALSE | “Project skill and agent frontmatter hooks require **explicit folder trust** … Disabling folder trust does not authorize frontmatter hooks, including in YOLO mode.” |
| Project hooks from `.qwen/settings.json` run without asking by default. | ⚠️ PARTIAL | They run only with “your **approval of the exact configuration** … or **explicit folder trust**” — “A fresh default environment with neither an approval nor a trust decision executes no repository hooks; a headless run prints one stderr line when hooks are withheld.” |
| Skills are user-invoked slash commands. | ⚠️ PARTIAL | “Skills are **model-invoked** — the model autonomously decides when to use them based on your request and the Skill's description.” Typing `/<skill-name>` is only the explicit force; “If you previously ran a Skill with `/skills <skill-name>`, that syntax now just opens the Skills panel.” |
| Qwen Code only installs its own extension format. | ❌ FALSE | “Extensions and plugins from Gemini CLI Extensions Gallery, Claude Code Marketplace, Qoder, and the portable Agent Plugins v1 format can be directly installed into Qwen Code”; Claude plugins are auto-converted (“`claude-plugin.json` is converted to `qwen-extension.json`”). |
| Agent Plugins v1 `allowed-tools` grants pre-approved tools. | ❌ FALSE | “The experimental `allowed-tools` field is recognized as a string but does not grant pre-approved Qwen tools.” |
| Subagents run in the foreground by default. | ❌ FALSE | “Top-level regular subagents run in the background by default and deliver their results through completion notifications”; `"agents": {"defaultBackground": false}` opts into foreground. |
| Omitting `subagent_type` forks the conversation. | ❌ FALSE | “Omitting `subagent_type` does **not** fork; it launches the general-purpose subagent.” Fork is explicit: `subagent_type: "fork"`. |
| `fork_tools` is an administrator-enforced security sandbox. | ⚠️ PARTIAL | “It narrows a child fork's capabilities but is not an administrator-enforced security sandbox because the caller can omit or expand the list.” |
| Fork subagents can spawn their own subagents. | ❌ FALSE | “Fork children cannot spawn any further sub-agent. This is enforced at runtime — if a fork calls the Agent tool, it receives an error instructing it to execute tasks directly.” |
| Codex subagents inherit the Qwen session's approval mode semantics. | ⚠️ PARTIAL | “Without an agent override, default, plan, and auto sessions use a read-only sandbox; Qwen's AUTO classifier does not inspect native commands.” Plus: “Explicitly select auto-edit in the session or Codex agent definition to allow workspace writes and unattended workspace commands, or yolo for full access.” |
| Agent Board actors are authenticated. | ❌ FALSE | “`--as` is a label recorded with the action, not authentication. There is no membership list, join command, heartbeat, or reserved participant name.” |
| Cross-session messaging is off by default. | ❌ FALSE | “`agents.crossSessionMessaging` … On by default: this session is discoverable by the others”; a workspace may only set it to `false`. |
| `tools.executionSandbox` confines the whole CLI everywhere. | ⚠️ PARTIAL | It is “an operator-only Linux policy” — “System policy replaces the complete User/SystemDefaults object; Workspace values are ignored” — and “ACP, `qwen serve` and web terminals explicitly reject it.” It confines tool execution, not the CLI itself. |
| Approving tools or running YOLO expands the sandbox policy. | ❌ FALSE | “Approval and YOLO do not expand the filesystem or network policy.” |
| The Linux execution sandbox hides host files from commands. | ⚠️ PARTIAL | “Reads remain broad: this mode does not hide host secrets or promise to isolate pathname Unix sockets and host services.” It bounds writes (`read-only`/`workspace-write`) and, with bwrap, network. |
| All variables in a project `.env` file are loaded. | ⚠️ PARTIAL | Loader-affecting variables — “`NODE_OPTIONS`, … `NODE_PATH`, `OPENSSL_CONF` … `LD_PRELOAD`, `LD_AUDIT`, `DYLD_INSERT_LIBRARIES`, `BASH_ENV`, `ZDOTDIR` … — are never loaded from `.env` files (any scope, including `.qwen/.env` and user-level files) or from the top-level `settings.json` `env` section,” and `DEBUG`/`DEBUG_MODE` are excluded from project `.env` by default. |
| The `settings.json` `env` section can set `NODE_OPTIONS`. | ❌ FALSE | Same rejection list: loader-affecting keys are “never loaded from `.env` files (any scope …) or from the top-level `settings.json` `env` section … To use one of these variables, export it in the environment you launch Qwen Code from.” |
| Usage statistics are opt-in. | ❌ FALSE | `QWEN_USAGE_STATISTICS_ENABLED` “Overrides the `privacy.usageStatisticsEnabled` setting. Defaults to enabled when neither is configured.” |
| MCP `trust: true` follows automatically from a trusted folder. | ⚠️ PARTIAL | “Server trust (`trust: true`): bypasses confirmation prompts for that server **only in a trusted workspace**” — both the per-server flag and the trusted workspace are required. |
| MCP connection-loss replay retries any tool. | ❌ FALSE | Replay happens “only … when the server has `trust: true`, the workspace is trusted, and the tool explicitly declares either `idempotentHint: true` or a consistent read-only annotation”; otherwise “Qwen Code reports that the result may be unknown.” |
| MCP OAuth always redirects to localhost. | ⚠️ PARTIAL | “By default, Qwen Code uses `http://localhost:7777/oauth/callback`”; on remote servers “the default `localhost` redirect will NOT work. Configure `--oauth-redirect-uri` with a public URL ending in `/oauth/callback`, then reverse-proxy that path” — “Qwen Code does not terminate TLS.” |
| `qwen serve` on loopback requires a token. | ❌ FALSE | “**Loopback is trusted by default** — `127.0.0.1:4170` starts without bearer authentication, and every local process that can reach it receives full API authority, including code execution as the daemon user.” |
| `qwen serve` is a multi-user server. | ⚠️ PARTIAL | “**Multi-workspace is single-operator** — registered workspaces share the daemon's bearer token, listener, quotas, and process fault boundary. Use separate daemons and an external orchestrator for independent users or security principals.” |
| Scheduled tasks fire on schedule regardless of session state. | ⚠️ PARTIAL | “Tasks only fire while Qwen Code is running and idle … If Qwen Code is busy when a task comes due, the prompt waits until the current turn ends,” with “No catch-up for missed fires” and deterministic jitter (recurring tasks “fire up to 10% of their period late, capped at 15 minutes”). |
| Configuring a channel enables scheduled-task delivery automatically. | ❌ FALSE | “Delivery is off by default. Configuring a Channel alone does not enable delivery for any task.” |
| Channel/webhook unattended tasks can run in default approval mode. | ❌ FALSE | “`approvalMode` … Tool approval mode for channel sessions. Unattended webhook tasks require `yolo`; the setting applies to every session on the channel.” |
| Headless runs exit 0 on budget overrun. | ❌ FALSE | Budget aborts emit “a structured `FatalBudgetExceededError` (exit code **55**) — distinct from the turn-cap exit code 53 and SIGINT's 130 so CI scripts can branch on the reason.” |
| `CI=true` enables persistent retry on rate limits. | ❌ FALSE | `QWEN_CODE_UNATTENDED_RETRY` “Must be set explicitly — `CI=true` alone does **not** activate this mode.” |
| The `Learning` output style works in headless runs. | ❌ FALSE | “`Learning` asks you to write part of the code and waits for a reply, so it is skipped in headless runs.” |
| `--max-tool-calls` bounds subagent inner work. | ⚠️ PARTIAL | “**`--max-tool-calls` counts top-level dispatches only.** When the model calls the `agent` tool, the dispatch counts as **1**; inner tool calls performed by the spawned subagent are **not** counted.” |
| `structured_output` retry loops are bounded by `--max-tool-calls`. | ❌ FALSE | “The exemption is unconditional (including failed Ajv validations), so a model stuck in a malformed-output retry loop is NOT bounded by `--max-tool-calls`; combine with `--max-session-turns` or `--max-wall-time`.” |
| The `/goal` verifier runs commands to check completion. | ❌ FALSE | “The verifier never runs commands. It judges from what is already in the transcript: the records of this Goal, read from the most recent one backwards.” |
| The QwenCloud/ModelStudio `web_search` tool needs extra setup. | ❌ FALSE | “Both access methods also enable the built-in `web_search` tool with no extra setup.” |
| `.qwenignore` changes apply live. | ⚠️ PARTIAL | Rules follow gitignore conventions, but “To apply the changes, you must restart your Qwen Code session.” |
