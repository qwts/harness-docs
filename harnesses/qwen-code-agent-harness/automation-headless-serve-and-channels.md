# Automation: headless, serve/daemon, channels, and SDKs

**Verified:** 2026-11-16 (Qwen Code 0.27.4 npm latest; docs site main)

## Headless mode

“Headless mode allows you to run Qwen Code programmatically from command line scripts and automation tools without any interactive UI.” Invocation: `qwen --prompt "..."` (`-p`), stdin pipes (`echo "Explain this code" | qwen`), file redirects. Resume: `qwen --continue -p "..."` / `qwen --resume <sessionId> -p "..."` — “Reuse conversation context from the current project in headless scripts.”

Output formats: `text` (default), `json` (“A JSON array … All messages are buffered and output together with the terminal result”; message types `system`/`assistant`/`result` with `is_error`, `duration_ms`, `usage`), `stream-json` (“emits JSON messages immediately as they occur during execution”; “This format uses line-delimited JSON where each message is a complete JSON object on a single line”), plus `--include-partial-messages` (“emits stream events (message_start, content_block_delta, etc.)”). “Textual `tool_result.content` values are bounded to 65,536 UTF-8 bytes after JSON string serialization” across JSON modes, SDK transports, subagents, and Dual Output. `--input-format stream-json` provides “JSON message protocol via stdin for bidirectional communication” (requires `--output-format stream-json`).

Structured output: `--json-schema` — “Constrain the model's final answer to a JSON Schema you supply. Qwen Code registers a synthetic terminal tool the model is required to call … The first valid call ends the run. Headless only.” In text mode “stdout is reserved for the JSON payload on success and is empty on failure; error messages and log lines go to stderr.”

Exit codes and budgets: “a budget abort emits a structured `FatalBudgetExceededError` (exit code **55**) — distinct from the turn-cap exit code 53 and SIGINT's 130 so CI scripts can branch on the reason.” Budgets: `--max-wall-time` (`90`, `30s`, `5m`, `1h`, `1.5h`; min 1s), `--max-tool-calls` (top-level dispatches; “the `agent` tool … counts as **1**; inner tool calls … are **not** counted”; `structured_output` is exempt), `--max-session-turns` (exit 53; `structured_output` is **not** exempt — “Size `--max-session-turns` to `N+1` if you want to allow `N` real-work turns”). “In stream-json input mode the daemon resets the budget counters at the start of every user message; the budget is per-message, not per-process.” And: “`qwen serve` / ACP sessions: the daemon ACP session path does NOT currently consult `--max-wall-time` / `--max-tool-calls` from settings.json.”

Persistent retry: `QWEN_CODE_UNATTENDED_RETRY=1` — “transient API capacity errors (HTTP 429 Rate Limit and 529 Overloaded) are retried indefinitely with exponential backoff (capped at 5 minutes per retry) and heartbeat keepalives every 30 seconds on stderr … Must be set explicitly — `CI=true` alone does **not** activate this mode.” System-prompt controls: `--system-prompt` (“Loaded context files such as `QWEN.md` are still appended after this override”), `--append-system-prompt`, `--output-style` (“`Learning` … is skipped in headless runs”). `/goal` works headless (“Goal state is stored with the session, so use `--continue` or `--resume <sessionId>` to inspect or control the same Goal from a later process”; with `--output-format stream-json`, “each Goal status change emits a `stream_event` whose `event.type` is `goal_state`”). `--safe-mode` disables all customizations for isolating problems.

**Dual Output** — “a sidecar mode for the interactive TUI: while Qwen Code keeps rendering normally on `stdout`, it concurrently emits a structured JSON event stream to a separate channel” (`--json-fd` / `--json-file`). “It also provides a reverse channel: an external program can write JSONL commands into a file that the TUI watches, allowing it to submit prompts and respond to tool-permission requests.” “Tool-approval prompts appear in both places; whoever approves first wins.”

## `qwen serve` (daemon) and Web Shell

“Run Qwen Code as an HTTP daemon so multiple clients (IDE plugins, web UIs, CI scripts, custom CLIs) can share agent sessions over HTTP + Server-Sent Events instead of each spawning their own subprocess. … **Status:** Experimental.” Default listener `http://127.0.0.1:4170` with a built-in **Web Shell** UI (`--no-web` for API-only; `--open` launches a browser). Highlights: “**Reconnect-safe streaming** — SSE with `Last-Event-ID` reconnect”; “**Paged persisted transcripts**”; “**First-responder permissions** — … whichever client answers first wins”; “**One daemon, one or more workspaces** — repeat `--workspace` … The first workspace is primary”; “**Experimental daemon-managed channels** — start with `qwen serve --channel <name>`”; remote runtime control endpoints (session approval mode, workspace tool/skill enable, `POST /workspace/init` — “mechanical only — does NOT call the model”, MCP restart/add/remove without daemon restart); `POST /session/:id/recap` (“a pure-cost endpoint … the daemon has no per-route rate limit in v1”).

Security posture: “**Loopback is trusted by default** — `127.0.0.1:4170` starts without bearer authentication, and every local process that can reach it receives full API authority, including code execution as the daemon user. Use a stable `QWEN_SERVER_TOKEN` with `--require-auth` on shared or untrusted hosts.” “**Non-loopback listeners always carry a bearer token** … Generated tokens rotate on restart … HTTP is unencrypted; configure TLS before crossing untrusted networks.” “**Multi-workspace is single-operator**.” `qwen daemon start` provides local lifecycle management (with `--save-token` storing a bearer “in an owner-only sidecar”); systemd/launchd/tmux/nohup templates are documented for service supervision. `serve.maxSessions` (default 32) caps “concurrent live sessions” per workspace. Remote phone/Web Shell access is “off by default” behind **Settings → Connections → Allow remote connections**. `QWEN_CONVERSATIONS_DIR` fixes the daemon's shared Conversations root for its lifetime.

## Scheduled tasks and channels

`/loop` (“the bundled skill”) schedules recurring prompts — “Qwen Code parses the interval, converts it to a cron expression, schedules the job, and confirms the cadence and job ID,” firing the prompt once immediately. Bare `/loop` starts “a self-paced autonomous loop.” One-shot reminders come from natural language (“remind me at 3pm to …”). Underlying tools: `CronCreate` (“Accepts a 5-field cron expression, the prompt …, whether it recurs or fires once, and an optional gate command”), `CronList`, `CronDelete` (8-character IDs; “A session can hold up to 50 scheduled tasks at once”). Gates: “a shell command that runs at each fire time, outside the model. If it prints nothing and exits 0, the fire is skipped … If it prints output, the task's prompt runs with that output attached.” Gates must be foreground (“a command that puts any part of itself in the background with `&` is refused”; `bash -c '…'` wrappers refused). Constraints: “Tasks only fire while Qwen Code is running and idle”; local timezone; deterministic jitter (“Recurring tasks fire up to 10% of their period late, capped at 15 minutes … One-shot tasks scheduled for the top or bottom of the hour … fire up to 90 seconds early”); “Recurring tasks automatically expire 7 days after creation by default” (`experimental.cronRecurringMaxAgeDays`, env `QWEN_CODE_CRON_MAX_AGE_DAYS`). Enabled by default via `experimental.cron: true` (`QWEN_CODE_DISABLE_CRON=1` disables). “Messaging channels use a separate persistent scheduler”; the Web Shell's Scheduled Tasks page can deliver completed run responses through a channel (“Delivery is off by default”; “Tasks that create a fresh session for each run (`per_run`) do not support delivery”; requires the daemon's `channel_delivery` capability).

**Channels** — “Channels let you interact with a Qwen Code agent from messaging platforms like Telegram, WeChat, QQ, DingTalk, WeCom, or Feishu … Code-hosting platforms (starting with GitHub) and authenticated workspace accounts (starting with DingTalk Workspace) are also supported … [Email] connects a dedicated mailbox through IMAP and SMTP.” “When you run `qwen channel start`, Qwen Code … Spawns a single agent process using the Agent Client Protocol (ACP) … All channels share one agent process with isolated sessions per user.” Types: `telegram`, `weixin`, `qq`, `dingtalk`, `dingtalk-webhook`, `dws`, `wecom`, `wecom-callback`, `feishu`, `feishu-webhook`, `github`, `gitlab`, `email`, or “a custom type from an extension.” Key options: `token`/`clientId`/`clientSecret` (all support `$ENV_VAR` syntax), `privatePolicy` (`disabled`/`allowlist`/`pairing`/`open`; “new managed channels default to `pairing`”), `sessionScope` (`user` default; `chat_thread`; `single`), `sessionRotation`, `multiSession` (up to eight owner-scoped tasks), `cwd`, `approvalMode` (“Unattended webhook tasks require `yolo`”), `instructions`, `groupPolicy` (default `disabled`), `operators`, `messageRoutes` (prefix routing; “The longest matching prefix wins”), `dispatchMode` (`steer` default / `collect` / `followup`), `webhooks` (daemon-managed webhook-triggered tasks). Channel memory keeps durable context for channel chats; auto-memory extraction skips channel-relayed turns.

## SDKs and APIs

- **TypeScript SDK** — `@qwen-code/sdk` — “A minimum experimental TypeScript SDK for programmatic access to Qwen Code” (Node.js ≥ 22).
- **Python SDK** — “`qwen-code-sdk` is an experimental Python SDK … v1 targets the existing `stream-json` CLI protocol and keeps the transport surface small and testable” (Python ≥ 3.10; “external `qwen` executable is required in v1”; process transport only).
- **Java SDK** — documented (`developers/sdk-java.md`).
- **REST API / daemon client** — `developers/daemon-rest-api-reference.md` (OpenAPI spec in-tree), `rest-api-integration.md`, and the `qwen-serve-protocol` developer page; the daemon exposes SSE event buses per session and extMethod RPCs (workspace MCP/skills/providers status, MCP restart).
- **GitHub Action** — `qwen-code-action`: “Trigger workflows based on events … or schedules”; “@qwencoder /review” mentions; configured with a `QWEN_API_KEY` secret (DashScope key) and repo `QWEN.md`.

## IDE and desktop surfaces

- **VS Code companion** (Beta): “Currently, the only supported IDE is Visual Studio Code and other editors that support VS Code extensions.” Setup by “**Automatic Nudge**”, `/ide install`, or marketplace. “**Workspace Context:** … The **10 most recently accessed files** … Your active cursor position. … Any text you have selected (up to a 16KB limit …).” “**Native Diffing:** … directly within your IDE's native diff viewer”; palette commands “Qwen Code: Run”, “Qwen Code: Accept Diff”, “Qwen Code: Close Diff Editor”, and “Qwen Code: View Third-Party Notices.”
- **Zed** — `--acp` (“Enables ACP mode (Agent Client Protocol) … Stable. Replaces the deprecated `--experimental-acp` flag”); worktree paths are passed as the ACP session `cwd`.
- **JetBrains** — dedicated integration page (`integration-jetbrains.md`).
- **Computer Use / Browser Use** — “Computer Use runs through the standalone Node REPL MCP server. Its first `js` call loads global `cua`”; the chain is “Qwen Code / any MCP client -> `@qwen-code/node-repl-mcp` (js, js_reset) -> `@qwen-code/cua-sdk/runtime` -> native Qwen CUA Driver (desktop applications) -> `@qwen-code/browser-use`”; Windows UIAccess requires “a signed worker under `Program Files\Qwen\CuaDriver`” (`CUA_DRIVER_USE_UIACCESS=1`).
- **LSP** (experimental) — “set `tools.lspEnabled` in your user `settings.json`” or `--experimental-lsp`; “Servers are configuration-driven. You must define them in `.lsp.json` (or via extensions)”; refused in safe mode, bare mode, read-only hosts, SSH, and provisional workspaces.
